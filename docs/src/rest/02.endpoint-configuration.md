# Endpoint Configuration

In the [Get Started](01.introduction.md#get-started) section, the Course Set used one path for all its operations, while Student Get Page used a path configured for one operation. Endpoint configuration determines which path or request Flux.REST uses for each Set operation.

This page continues from those examples. It begins with common path configurations, then explains how operation parameters provide path and query values.

## Configure Paths

A path configuration can apply at three levels:

- all operations;
- a specific HTTP method;
- a specific operation.

Use this broad-to-specific order in configuration code: add a general `WithEndpoint` first, then add method-specific or operation-specific configurations. Each narrower configuration replaces the general one only for the operations it matches.

### One Path for a Set

`WithEndpoint` configures one endpoint path for all supported operations in a Set:

```csharp
.AddSet<Course, int>()
    .WithEndpoint("courses")
```

With the Service base URL from Get Started, calling `courseSetContext.GetAsync(42)` produces:

```text
https://school-api.example.com/courses/42
```

Flux.REST creates the request URL by joining the non-empty parts in this order:

```text
Service base URL / Set path / endpoint path / operation identifier
```

Here, `UsingRest` provides the Service base URL, `WithEndpoint` provides the endpoint path, and `GetAsync(42)` provides the operation identifier.

Alternatively, configure the same path when adding the Set:

```csharp
.AddSet<Course, int>(path: "courses")
```

### Paths by HTTP Method

Use a method-specific helper when operations that use different HTTP methods need different paths. Each helper applies its path to these built-in operations:

| Helper | Operations |
| --- | --- |
| `WithGet("path")` | GetAsync, GetAllAsync, and GetPageAsync |
| `WithPost("path")` | AddAsync without an identifier |
| `WithPut("path")` | AddAsync with an identifier and non-partial UpdateAsync |
| `WithPatch("path")` | Partial UpdateAsync |
| `WithDelete("path")` | RemoveAsync |

### A Path for an Operation

The Student Set uses `students` for `GetAsync`, while `GetPageAsync` uses a path nested beneath a course. Both operations use `GET`, so `WithGet("path")` would configure both. To configure only `GetPageAsync`, use its operation descriptor type as the lambda parameter:

```csharp
.WithEndpoint((GetPageOperationDescriptor _) => "courses/{courseId}/students")
```

For `GetPageAsync`, this configuration replaces the general `students` endpoint with the nested path. 

The `{courseId}` is a path placeholder. The next section shows how to provide its value.

## Operation Parameters

Operation parameters provide values for path placeholders and query parameters.

### Named Parameters

Named parameters pair each value with a name. Flux.REST can use that name for a path placeholder or a query parameter:

```csharp
var parameters = new OperationParameterCollection(
    new[]
    {
        new KeyValuePair<string, object>("courseId", 42),
        new KeyValuePair<string, object>("status", "active")
    });

var studentsPage = await studentSetContext.GetPageAsync(
    offset: 0,
    limit: 20,
    parameters: parameters);
```

For the path configured earlier, `courseId` replaces the `{courseId}` placeholder. The `status` parameter is not used by the path, so Flux.REST adds it to the query string. Get Page also adds its non-null `offset` and `limit` values:

```text
https://school-api.example.com/courses/42/students?status=active&offset=0&limit=20
```

Parameter names must match placeholders exactly, including uppercase and lowercase letters. Named parameters must provide a value for every placeholder in the path.

### Positional Parameters

You can also provide parameter values without names:

```csharp
var parameters = new OperationParameterCollection(new object[] { 42, 7 });
```

Positional values replace placeholders from left to right, regardless of the placeholder names. For example:

```text
courses/{courseId}/students/{studentId}
```

becomes:

```text
courses/42/students/7
```

The number of positional values must exactly match the number of placeholders.

### Control Automatic Query Parameters

By default, Flux.REST keeps any query string already present in the configured path, then adds unused named parameters and pagination values.

Set the path helper's `queryComplete` argument to `true` when the configured query string is already complete.

For example, suppose the school API expects `skip` and `take` instead of `offset` and `limit`. Build those query parameters from the page request and mark the query as complete:

```csharp
.WithEndpoint((GetPageOperationDescriptor operation) =>
{
    var skip = operation.PageRequest.Offset;
    var take = operation.PageRequest.Limit;
    return $"courses/{{courseId}}/students?skip={skip}&take={take}";
},
queryComplete: true)
```

Calling the Student Get Page operation now produces:

```text
https://school-api.example.com/courses/42/students?skip=0&take=20
```

The resolver reads the requested pagination values and assigns the names expected by the API. Flux still replaces the `courseId` placeholder, but `queryComplete: true` prevents it from also appending the default `offset` and `limit` parameters.
